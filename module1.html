Задание 1.1

Как работают языковые модели

Что делаем: собираем «игрушечную» языковую модель и сами реализуем всё, что происходит между выходом нейросети и готовым текстом: softmax с температурой, top-k, top-p, выбор токена и цикл генерации. Зачем: чтобы без магии увидеть, что модель выдаёт не слово, а распределение вероятностей; что разные ответы на один вопрос — не баг, а выбор из этого распределения; и что «галлюцинация» — нормальная работа механизма, когда фактов нет.

Теория-минимум

  • LLM — это функция «контекст → распределение вероятностей следующего токена». Текст получается циклом (авторегрессия): выбрали токен → дописали в контекст → повторили, пока модель не выдаст специальный токен конца (<eos>) или не упрётся в лимит max_tokens.
  • Сеть выдаёт не вероятности, а логиты — произвольные числа по одному на каждый токен словаря. softmax превращает их в вероятности: pi = exp(zi / T) / Σ exp(zj / T).
  • Температура T делит логиты: T < 1 — выбор «острее» (почти всегда самый вероятный токен), T > 1 — «ровнее» (больше разнообразия и больше риска получить нелепость). T = 0 — жадный выбор (argmax).
  • top-k и top-p (nucleus) обрезают «хвост» маловероятных токенов до выбора: top-k оставляет k лучших, top-p — минимальный набор, чья суммарная вероятность не меньше p. Так высокая температура перестаёт приводить к случайному мусору.
  • seed делает выбор воспроизводимым. В облачных API это «best effort»: одинаковые параметры не гарантируют ответы побайтно (параллельные вычисления, батчинг, обновления модели).
  • Модель не хранит состояние между вызовами. «Память» чата — это история, которую клиент каждый раз отправляет заново (на этом держится задание 1.2).
  • Галлюцинация — не поломка, а следствие механизма: модель всегда выбирает правдоподобное продолжение и не имеет встроенного режима «не знаю». Риск снижают фактами в контексте, инструкцией «если нет в материалах — скажи», низкой температурой для фактов и проверкой ответа.
  • Причина остановки (finish_reason): stop — модель закончила сама, length — ответ обрезан лимитом.

/** Источник псевдослучайных чисел из [0, 1). */
export type Rng = () => number;

/** Генератор с seed (mulberry32): один seed — всегда одна и та же последовательность. Дан. */
export function seededRng(seed: number): Rng {
  let a = seed >>> 0;
  return () => {
    a = (a + 0x6d2b79f5) >>> 0;
    let t = a;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

export const EOS = "<eos>"; // токен «конец ответа»

/** Модель — это функция «контекст → оценки (логиты) для каждого токена словаря». Состояния у неё нет. */
export interface LanguageModel {
  vocab: string[];
  nextLogits(context: string[]): number[];
}

/** Модель «по подсчёту частот»: что в корпусе чаще всего шло после последних 1–2 слов. Дана. */
export class NGramModel implements LanguageModel {
  readonly vocab: string[];
  private table = new Map<string, Map<string, number>>();

  constructor(corpus: string, private readonly order = 3) {
    const sentences = corpus
      .trim()
      .split("\n")
      .map((line) => [...line.trim().split(/\s+/), EOS]);
    this.vocab = [...new Set(sentences.flat())];
    for (const tokens of sentences) {
      for (let i = 1; i < tokens.length; i++) {
        for (let n = 1; n < order && n <= i; n++) {
          const key = tokens.slice(i - n, i).join(" ");
          const row = this.table.get(key) ?? new Map<string, number>();
          row.set(tokens[i], (row.get(tokens[i]) ?? 0) + 1);
          this.table.set(key, row);
        }
      }
    }
  }

  nextLogits(context: string[]): number[] {
    // «откат»: берём самый длинный хвост контекста, который встречался в корпусе
    for (let n = Math.min(this.order - 1, context.length); n >= 1; n--) {
      const row = this.table.get(context.slice(-n).join(" "));
      if (row) return this.vocab.map((token) => Math.log((row.get(token) ?? 0) + 0.001));
    }
    return this.vocab.map(() => 0); // контекст незнаком — все токены одинаково вероятны
  }
}

const sum = (xs: number[]) => xs.reduce((a, b) => a + b, 0);
const entropy = (ps: number[]) => -sum(ps.filter((p) => p > 0).map((p) => p * Math.log(p)));

const model = new NGramModel(CORPUS);
const prompt = ["небо", "днём"];

/** Распределение следующего токена после контекста в виде { токен: вероятность }. */
const dist = (context: string[], temperature = 1) => {
  const probs = softmax(model.nextLogits(context), temperature);
  return Object.fromEntries(model.vocab.map((token, i) => [token, probs[i]]));
};

describe("A. softmax и температура", () => {
  it("возвращает распределение: сумма = 1, порядок токенов сохраняется", () => {
    const p = softmax([2, 1, 0]);
    expect(sum(p)).toBeCloseTo(1);
    expect(p[0]).toBeGreaterThan(p[1]);
    expect(p[1]).toBeGreaterThan(p[2]);
  });

  it("устойчив к большим логитам: без NaN и Infinity", () => {

    expect(p.every(Number.isFinite)).toBe(true);

Самопроверка

1. Что модель возвращает на каждом шаге — токен или распределение?

Распределение (логиты по всему словарю). Конкретный токен выбирает код вокруг модели (сэмплинг) — в облачном API это делает сервер. Поэтому один и тот же запрос может давать разные ответы.

2. Почему temperature: 0 в облачных API не гарантирует одинаковых ответов?

Жадный выбор детерминирован только на бумаге. В реальности результат плавает из-за неассоциативности операций с плавающей точкой при параллельных вычислениях на GPU, батчинга запросов, разных реплик и версий модели. Вывод: тесты на LLM не должны требовать побайтного равенства.

3. Чем top-k отличается от top-p и почему top-p часто практичнее?

top-k фиксирует число кандидатов, top-p — их вероятностную массу. Когда модель уверена, top-p оставит один-два токена, когда сомневается — много; k не подстраивается. Обычно настраивают что-то одно: либо температуру, либо top-p.

4. Почему про «Атлантиду» модель называет город? Как снизить такой риск?

Она продолжает текст по статистике и не имеет режима «не знаю»: самый правдоподобный шаблон «столица X — <город>». Снижают риск так: дают факты в контексте и требуют отвечать только по ним, фиксируют T = 0 для фактов, просят цитаты/источники, проверяют ответ, а при отсутствии материалов вообще не вызывают модель (так будет в итоговом задании).

5. Модель stateless. Как же чат «помнит» прошлые реплики и что это значит для денег?

Клиент каждый раз отправляет всю историю как часть контекста. Значит, длинный диалог дорожает с каждой репликой — это количественно разберём в задании 1.2.

6. Что делать, если finish_reason = "length"?

Ответ обрезан: его нельзя считать полным (особенно JSON). Увеличьте лимит, попросите ответить короче или продолжите генерацию отдельным запросом. Хороший клиент всегда возвращает причину остановки.

7. Вероятности «мусорных» токенов исходно ничтожны. Почему при T = 2 они вдруг заметны?

Температура делит логиты, и «хвост» подтягивается к лидерам. Суммарная масса десятков токенов с вероятностью ~0,0002 выросла до ~10% — за несколько шагов мусор практически гарантирован. Top-p/top-k отсекают хвост до выбора.

Задание 1.2

Токены, контекст и стоимость

Что делаем: учимся измерять текст в токенах и переводить токены в деньги и в «занятое место» контекстного окна. Зачем: токен — единица, в которой измеряются цена, лимиты и скорость. Пока вы не умеете считать токены, вы не можете ни спланировать бюджет, ни объяснить, почему длинный диалог «вдруг» стал дорогим.

Теория-минимум

  • Токен — кусочек текста: часть слова, слово вместе с пробелом, знак препинания, а иногда лишь часть байтов одного символа. Словарь — десятки и сотни тысяч токенов, строится алгоритмом BPE (byte-pair encoding).
  • У разных семейств моделей разные токенизаторы: локальный подсчёт — это оценка, точные числа всегда приходят в поле usage ответа API.
  • Эмпирика: английская проза — около 4 символов на токен. Другие языки (в том числе русский) и «плотные» форматы — код, JSON, URL, длинные числа — дают заметно больше токенов на тот же объём, а значит стоят дороже и быстрее заполняют окно.
  • Контекстное окно — общий лимит «вход + выход» (у «думающих» моделей ещё и скрытые рассуждения). max_tokens ограничивает только ответ. Если вход + ответ не помещаются, запрос отклоняется или ответ обрезается.
  • Цена: (вход × цена_входа + выход × цена_выхода) / 1 000 000 при ценах за 1 млн токенов. Выходные токены, как правило, заметно дороже входных; кэшированная часть входа дешевле; токены рассуждений оплачиваются как выходные.
  • Модель stateless, поэтому на каждом ходу диалога в запрос уходит вся предыдущая переписка. Вход k-го хода растёт линейно, а суммарная стоимость диалога — квадратично (сумма арифметической прогрессии).

Самопроверка

1. Почему один и тот же смысл по-русски «дороже», чем по-английски? Что из этого следует?

Токенизатор обучен на смеси с перекосом в английский, поэтому русские слова чаще дробятся на мелкие куски. Цена и окно считаются в токенах — тот же текст стоит дороже и занимает больше места. Вывод: считать токены на реальных данных, а не по числу слов.

2. Зачем при проверке окна добавлять max_tokens к входу?

Вход и ответ делят одно окно. Если вход + max_tokens больше окна, провайдер вернёт ошибку или обрежет ответ. У «думающих» моделей скрытые рассуждения тоже расходуют лимит — слишком малый max_tokens оставит пустой ответ.

3. Диалог из 30 ходов: system 500 токенов, пара «вопрос + ответ» — 200. Сколько входных токенов оплачено суммарно?

Приблизительно 30·500 + 200·(0+1+…+29) = 15 000 + 87 000 ≈ 100 000, хотя «полезного» текста в диалоге около 6 000. Вдвое больше ходов — примерно вчетверо больше входа.

4. Что выгоднее: убрать 1 000 токенов из промпта или из ответа?

Выходные токены дороже, да и генерируются последовательно (задержка). Но промпт повторяется в каждом запросе, а стабильный префикс ещё и кэшируется (дешевле). Решает расчёт на ваших цифрах — для этого и нужен estimateCost.

5. Почему countChatTokens не равен usage.prompt_tokens?

Формула и токенизатор подходят для конкретного семейства моделей; у других провайдеров разметка и токенизатор иные, а описания инструментов, изображения и т. п. мы не учли. Для предварительной оценки берите запас; для учёта и биллинга — только usage.

6. Что такое reasoning-токены и как они меняют счёт?

Это «скрытые» токены размышления модели: в ответе их нет, но они оплачиваются как выходные и расходуют окно и лимит генерации. Поле usage обычно показывает их отдельно.

7. Почему склейка токенов эмодзи может не совпасть с исходной строкой?

Токены — фрагменты байтов UTF-8. Один символ (эмодзи, редкая буква) может быть разрезан между токенами, а decode одного токена даёт «�». Корректно декодировать нужно всю последовательность целиком.

Задание 1.3

Различия моделей и провайдеров

Что делаем: учимся различать модель, провайдера и формат API; пишем адаптеры, которые прячут отличия Anthropic и Gemini за единым интерфейсом, и функцию выбора модели по требованиям. Зачем: «подключить LLM» — это не одна строка. Провайдеры различаются форматом запроса и ответа, тем, что именно считается в usage, ценами и ограничениями. Осознанный выбор и слой-адаптер защищают от привязки к одному поставщику и от сюрпризов в счёте.

Теория-минимум

  • Три разных понятия: модель (веса и поведение), провайдер (кто её хостит и продаёт доступ: сам вендор, облако, агрегатор, ваш сервер) и формат API (OpenAI-совместимый, Anthropic Messages, Gemini generateContent). Одну модель могут предлагать несколько провайдеров с разными ценами и лимитами, а один провайдер — много моделей.
  • Классы моделей: small/fast (дёшево и быстро — классификация, извлечение, простые ответы), large/flagship (сложные инструкции, код, длинные документы), reasoning (думают перед ответом: дороже, медленнее, скрытые токены), embedding-модели (векторы для поиска — модуль 5) и open-weights (веса открыты — можно развернуть у себя).
  • Критерии выбора: качество на вашей задаче (не на бенчмарке), цена входа/выхода/кэша, окно контекста и максимальный выход, задержка (время до первого токена и скорость), возможности (vision, вызов инструментов, структурированный вывод), лимиты запросов, требования к данным (регион, хранение, договор), стабильность версий и сроки отключения моделей.
  • Форматы API различаются «ломающим» образом: где лежит system, обязателен ли max_tokens, как устроен ответ и что именно входит в поля usage (кэш, рассуждения). Сравнивать токены разных провайдеров можно только после нормализации.
  • «OpenAI-совместимый» не значит «идентичный»: параметры поддерживаются частично, имена полей и ошибки могут отличаться, у «думающих» моделей часть параметров (temperature) нельзя менять, а лимит ответа называется иначе (max_completion_tokens).
  • Модели и цены меняются каждые несколько месяцев, поэтому каталог моделей — это данные (конфиг с датой проверки), а не константы в коде.

  fetchFn: typeof fetch = fetch,
): Promise<NormalizedResponse & { latencyMs: number }> {
  const http = adapter.buildRequest(req, apiKey);
  const started = performance.now();
  const res = await fetchFn(http.url, { method: "POST", headers: http.headers, body: JSON.stringify(http.body) });
  if (!res.ok) throw new Error(`HTTP ${res.status}: ${(await res.text()).slice(0, 300)}`);
  const parsed = adapter.parseResponse(await res.json());
  return { ...parsed, latencyMs: Math.round(performance.now() - started) };
}

Частичная поддержка параметров, другое имя лимита ответа, расхождения в usage, ошибках, стриминге и вызове инструментов, ограничения у reasoning-моделей. Тестируйте именно тот эндпоинт, который будете использовать.

6. Зачем selectModel возвращает ranked и rejected, а не только chosen?

ranked — готовая цепочка запасных моделей (fallback при сбое — пригодится в итоговом задании); rejected с причинами делает выбор объяснимым и помогает понять, какое требование «убило» все варианты.

7. Когда оправдана локальная модель с открытыми весами?

Когда данные нельзя отправлять наружу, нужен офлайн или полный контроль версии, либо объём стабильно большой и железо окупается. Платите качеством относительно топовых облачных моделей и эксплуатацией (GPU, обновления, мониторинг).

Оптимизация расходов и контекста

Что делаем: учимся находить, на что уходят токены, и сокращать вход тремя приёмами: отбирать только релевантное, управлять историей диалога и раскладывать промпт так, чтобы сработал кэш префикса. Зачем: входной контекст — главная статья расходов в реальных приложениях. Оптимизация без измерения — гадание, а без проверки качества — риск.

Теория-минимум

  • Сначала измерить. Часто 80–90% входа — «статика»: документы, история, инструкции, примеры. Пока нет разбивки по частям, любая оптимизация — случайная.
  • Не отправлять лишнее. Вместо всего документа в запрос попадают только релевантные куски (retrieval — полноценно разберём в модуле 5). Это дешевле, быстрее и часто точнее: шум в контексте мешает модели, а информация в середине очень длинного контекста используется хуже («lost in the middle»).
  • Управлять историей. Скользящее окно (последние N токенов + закреплённый system) просто и бесплатно, но забывает раннее. Суммаризация старой части сохраняет суть, но стоит дополнительного вызова и может исказить детали.
  • Кэширование префикса. Если начало запроса совпадает с недавним, провайдер переиспользует вычисления: вход дешевле и быстрее. Работает только для одинакового префикса, поэтому порядок важен: сначала неизменное (инструкции, документ), в конце — меняющееся (время, пользователь, вопрос). Условия различаются у провайдеров (автоматически или явными маркерами, минимальная длина, срок жизни, цена записи и чтения) — читайте актуальную документацию.
  • Другие рычаги: выбрать модель по задаче (дешёвая по умолчанию, дорогая по сигналу), ограничить и «сжать» вывод (max_tokens, короткий формат), асинхронные batch-вызовы со скидкой, кэш ответов в приложении, меньше примеров в промпте.
  • Риски: пропали нужные факты, суммаризация исказила детали, кэш «ломается» мелочами (метка времени или ID в начале, другой порядок ключей или инструментов). Каждую оптимизацию проверяют на наборе контрольных вопросов: стоимость упала, а доля верных ответов — нет.

export function makeHandbook(paragraphs = 200): string {
  const rng = seededRng(2026);
  const factAt = new Map(FACTS.map((fact, i) => [Math.floor(((i + 1) * paragraphs) / (FACTS.length + 1)), fact]));
  const out: string[] = [];
  for (let n = 1; n <= paragraphs; n++) {
    const fact = factAt.get(n - 1);
    const sentences = fact
      ? [fact]
      : Array.from({ length: 3 }, () => FILLER[Math.floor(rng() * FILLER.length)]);
    out.push(`Пункт ${n}. ${sentences.join(" ")}`);
  }
  return out.join("\n\n");
}

Самопроверка

1. С чего начинать оптимизацию и почему не с «выбора другой модели»?

С замера (tokenBreakdown): он показывает, какая часть запроса даёт основную массу токенов. Часто это документ или история, и смена модели лишь сделает дорогой запрос чуть менее дорогим.

2. Почему «возьмём модель с окном 1 млн токенов» — плохая стратегия?

Вы платите за каждый токен в каждом запросе, растёт задержка, упираетесь в лимиты на токены в минуту, а качество на очень длинных контекстах может падать (шум, «lost in the middle»). Большое окно — запас на крайний случай, а не способ работы.

3. Скользящее окно или суммаризация — когда что?

Окно — когда важны только последние реплики: просто, детерминированно, бесплатно. Суммаризация — когда нужно помнить суть давнего: дороже и может исказить детали. Часто сочетают: system + резюме + последние N реплик.

4. Как работает кэш префикса и что его ломает?

Провайдер переиспользует вычисления для совпадающего начала запроса. Ломают: время/ID/имя в начале, перестановка частей, недетерминированная сериализация (порядок ключей JSON, инструментов), любое изменение system. Плюс есть минимальная длина префикса и срок жизни кэша.

5. Чем опасна агрессивная оптимизация и как проверить, что качество не упало?

Можно выбросить нужный факт или исказить его резюме. Проверка — набор контрольных вопросов с известными ответами (как QUESTIONS): сравните долю верных ответов и стоимость до и после. Это основа оценки качества (evals — модуль 4).

6. Где наш pickRelevantChunks по основам слов не найдёт ответ, хотя он есть?

Синонимы и перефразирование («отпуск» и «выходные дни»), опечатки, разные языки, вопрос без общих слов с текстом. Поэтому в модуле 5 вместо совпадения слов будут эмбеддинги и гибридный поиск.

7. Какие ещё приёмы снижения расходов вы знаете?

Дешёвая модель по умолчанию и эскалация по сигналу, лимит и компактный формат ответа, batch-режим со скидкой для несрочного, кэш ответов в приложении, меньше примеров в промпте, ограничение размера вложений.

Использование LLM через API

Что делаем: пишем собственный небольшой клиент для chat API на fetch: сборка запроса, разбор ответа, классификация ошибок, повторы с нарастающей паузой, таймаут и потоковая выдача (SSE). Зачем: на этом слое держится любое LLM-приложение. Ненадёжный клиент превращает короткий сбой провайдера в падение вашего продукта, а повторы «на авось» — в лишний счёт.

Теория-минимум

  • Вызов модели — обычный HTTP: POST + JSON. Заголовки (авторизация, content-type); тело — model, messages с ролями system / user / assistant и параметры. В ответе — текст, finish_reason, usage, id запроса.
  • Ключ API — секрет. Храним в переменных окружения или менеджере секретов, не коммитим, не отправляем из браузера (запросы идут через ваш сервер), ограничиваем лимитом расходов, не пишем в логи и сообщения об ошибках.
  • Ошибки. 4xx — «виноват запрос»: 400 (неверный запрос), 401/403 (ключ, права), 404 (модель), 413/422 (слишком большой или невалидный), 429 (лимит запросов или расходов); 5xx — сторона провайдера. Повторять имеет смысл 408, 429, 5xx, сетевые ошибки и таймауты; остальные 4xx от повтора не исправятся.
  • Повторы требуют дисциплины: лимит попыток, экспоненциальная пауза с jitter (случайным разбросом, чтобы клиенты не ломились синхронно), уважение заголовка Retry-After. Каждый повтор — это ещё один платный запрос.
  • Таймаут обязателен: без него зависший запрос держит ресурсы вечно. В fetch отмена делается через AbortController.
  • Стриминг (stream: true) отдаёт ответ по частям в формате SSE: строки data: {json}, в конце data: [DONE]. Выигрыш — время до первого токена и ощущение скорости. Цена — сложность: сеть режет поток где угодно, ошибка может случиться посреди ответа, а usage приходит в конце (в OpenAI-формате — только если запросить stream_options.include_usage).
  • Тестируемость. Клиент получает fetch, sleep и random снаружи (dependency injection) — поэтому тесты быстрые, без сети и без денег, а паузы и сбои воспроизводимы.

export type Step = Response | Error | ((init: RequestInit) => Promise<Response>);

export interface Call {
  url: string;
  init: RequestInit;
  body: any; // тело запроса, уже разобранное из JSON
}

/** fetch-двойник: каждый вызов получает следующий шаг сценария (ответ, ошибка или функцию). */
export function scriptedFetch(steps: Step[]) {
  const queue = [...steps];
  const calls: Call[] = [];
  const fn = (async (url: string | URL | Request, init: RequestInit = {}) => {
    calls.push({ url: String(url), init, body: init.body ? JSON.parse(String(init.body)) : undefined });
    const step = queue.shift();
    if (step === undefined) throw new Error("scriptedFetch: сценарий закончился, а запросы продолжаются");
    if (step instanceof Error) throw step;
    return typeof step === "function" ? step(init) : step;
  }) as typeof fetch;
  return { fn, calls };
}

/** «Зависший» сервер: молчит, пока запрос не отменят через AbortSignal. */
export const hang: Step = (init) =>
  new Promise<Response>((_, reject) => {
    init.signal?.addEventListener("abort", () => reject(new DOMException("The operation was aborted", "AbortError")));
  });

/** Текст → поток байт, нарезанный на куски по `size` байт (имитация фрагментации в сети). */
export function chunkedStream(text: string, size: number): ReadableStream<Uint8Array> {
  const bytes = new TextEncoder().encode(text);
  let offset = 0;
  return new ReadableStream<Uint8Array>({
    pull(controller) {
      if (offset >= bytes.length) return controller.close();
      controller.enqueue(bytes.slice(offset, offset + size));
      offset += size;
    },
  });
}

/** Ответ-стрим в формате SSE; события — объекты (будут сериализованы) или готовые строки. */
export const sseResponse = (events: unknown[], chunkSize = 16) =>
  new Response(
    chunkedStream(
      events.map((e) => `data: ${typeof e === "string" ? e : JSON.stringify(e)}\n\n`).join(""),
      chunkSize,
    ),
    { status: 200, headers: { "content-type": "text/event-stream" } },
  );

Самопроверка

1. Из чего состоит запрос к chat API и почему ключ нельзя отправлять из браузера?

Метод POST, URL, заголовки (авторизация и content-type) и JSON-тело. Ключ в браузере виден любому пользователю и будет украден — запросы к LLM делают с вашего сервера, а ключ лежит в секретах и ограничен лимитом расходов.

2. Какие ошибки повторять, а какие нет? Чем опасны повторы?

Повторять: 408, 429, 5xx, сетевые ошибки, таймауты. Не повторять: 400, 401, 403, 404, 422 — запрос не изменится и снова будет отклонён. Опасность повторов: лишние платные запросы, усиление перегрузки провайдера («шторм повторов») и задержка ответа пользователю.

3. Зачем нужны jitter и Retry-After?

Retry-After — прямая подсказка сервера, когда можно повторить. Jitter размазывает повторы разных клиентов по времени, чтобы они не ударили по серверу одновременно.

4. Как отличить «модель закончила» от «ответ обрезан»?

По finish_reason: stop — закончила сама, length — упёрлась в лимит. Обрезанный ответ (особенно JSON) нельзя считать полным.

5. Что даёт стриминг, если полное время генерации не меняется? Чем за это платим?

Улучшается время до первого токена и воспринимаемая скорость. Платим сложностью: разбор SSE на рваных границах, ошибка посреди потока, usage только в конце (и только если запросили), повторы после первых токенов исказили бы ответ.

6. Почему повторять запрос «на чтение» безопасно, а запрос с действиями — не всегда?

Повтор генерации текста идемпотентен (лишь цена и задержка). Если по ответу модели выполняются действия — отправка письма, платёж, запись в БД, — повтор может выполнить их дважды. Нужны ключи идемпотентности и проверки; подробнее — в модулях 6 (Tools и MCP) и 8 (Надёжность и безопасность).

7. Зачем клиенту внедряемые fetch, sleep и random?

Чтобы тесты не ходили в сеть, не ждали реальные секунды и были воспроизводимыми: сбои, паузы и случайность задаются сценарием. Это тот же принцип, что seed в задании 1.1.

Сценарий

В компании есть регламент (200 пунктов, около 11 тысяч токенов). Первая версия помощника работает «в лоб»: на каждый вопрос отправляет в самую мощную модель весь регламент и всю историю чата. Вопросов будет много (около 500 сотрудников × несколько вопросов в день), поэтому нужна версия, которая:

№ Требование Тема
1 На точные вопросы отвечает одинаково при каждом запуске, на творческие («придумай…») — с разнообразием. Если в регламенте нет материалов по теме — не выдумывает ответ и не тратит деньги на вызов модели. 1.1

// Сервер делает вид, что понимает вопросы по регламенту: если нужный факт есть в запросе, он становится

import { FACTS, QUESTIONS } from "../src/fixtures";

const IDEAS = [
  "Идея А: тематический квиз для отдела",
  "Идея Б: встреча на свежем воздухе",
  "Идея В: командный воркшоп по кулинарии",
  "Идея Г: экскурсия по городу",
];
const WRONG = ["Точных сведений нет, обычно — не более недели.", "Вероятно, это определяется приказом руководителя."];

type Candidate = { text: string; logit: number };

function choose(candidates: Candidate[], temperature: number, rng: () => number): string {
  try {
    const probs = softmax(candidates.map((c) => c.logit), temperature);
    return candidates[sampleIndex(probs, rng)].text;
  } catch (e) {
    throw new Error(`Подставной LLM использует ваши softmax и sampleIndex из задания 1.1: ${(e as Error).message}`);
  }
}

function answerFor(body: any, rng: () => number): string {
  const request: string = body.messages.map((m: { content: string }) => m.content).join("\n");
  const last: string = body.messages.at(-1).content;
  const temperature: number = body.temperature ?? 1;

  if (last.includes("Придумай")) {
    return choose(IDEAS.map((text, i) => ({ text, logit: 2 - 0.5 * i })), temperature, rng);
  }
  const asked = QUESTIONS.find(({ q }) => last.includes(q));
  const fact = asked && FACTS.find((f) => f.includes(asked.needle));
  const candidates: Candidate[] = WRONG.map((text, i) => ({ text, logit: 2.5 - 0.5 * i }));
  if (fact && request.includes(fact)) candidates.unshift({ text: fact, logit: 3 }); // факт есть в запросе
  return choose(candidates, temperature, rng);
}

const chatTokens = (messages: { role: string; content: string }[]) =>
  messages.reduce((sum, m) => sum + 3 + countTokens(m.role) + countTokens(m.content), 3);

export function fakeLLM(options: FakeOptions = {}) {
  const rng = seededRng(options.seed ?? 1);
  const flaky = Object.fromEntries(Object.entries(options.flaky ?? {}).map(([k, v]) => [k, [...v]]));
  const calls: Call[] = [];
  const fn = (async (url: string | URL | Request, init: RequestInit = {}) => {
    const body = JSON.parse(String(init.body));
    calls.push({ url: String(url), init, body });
    const status = flaky[body.model]?.shift() ?? options.down?.[body.model];
    if (status) return failure(status);
    const text = answerFor(body, rng);
    return jsonResponse(
      {
        model: body.model,
        choices: [{ index: 0, message: { role: "assistant", content: text }, finish_reason: "stop" }],
        usage: { prompt_tokens: chatTokens(body.messages), completion_tokens: countTokens(text) },
      },
      200,
      { "x-request-id": `req_${calls.length}` },
    );
  }) as typeof fetch;
  return { fn, calls };
}

Шаг 5Защита: проверка понимания

Ответьте письменно или устно на любые пять вопросов из десяти (проверяющий может выбрать сам). Каждый вопрос связывает минимум две темы — угадать нельзя, нужно понимать.

1. [1.1 × 1.4] Что делает помощник на вопрос «Сколько дней отпуска на Марсе?» и почему он не вызывает модель? Как это связано с галлюцинациями?

Отбор не находит релевантных абзацев → возвращается «не нашёл», модель не вызывается. Если бы вызвали, она выбрала бы правдоподобное продолжение и «придумала» цифру (как с Атлантидой). Заодно экономим деньги.

2. [1.1 × 1.3] Почему для lookup температура 0 и класс small, а для brainstorm около 0,9 и large? Что будет, если поменять местами?

Факты требуют стабильности и дёшевы для small-модели; идеи требуют разнообразия и «ума». При T = 0 «мозговой штурм» выдаст один и тот же вариант; при высокой T точные ответы начнут «плыть» (мы это видим в тесте на 20 запусков).

3. [1.2] Откуда расхождение между оценкой входа и usage на реальном API и чему верить?

Другой токенизатор и разметка сообщений у провайдера, невидимые токены (инструменты, служебные). Оценка нужна для предварительной проверки бюджета (берём запас), а для учёта и биллинга источник правды — usage.

4. [1.2 × 1.4] Как изменится стоимость при росте истории с 10 до 40 реплик с обрезкой и без неё?

Без обрезки вход растёт линейно с историей, а суммарная стоимость диалога — квадратично. С обрезкой вход упирается в бюджет истории и перестаёт расти: цена хода почти постоянна.

5. [1.3 × 1.2] Как доказать, что small-модели хватает для lookup? Что потеряете, если small окажется недостаточной?

Прогнать контрольные вопросы с известными ответами на обеих моделях и сравнить долю верных ответов и стоимость. Если качество проседает — меняется политика (класс), а код конвейера остаётся: это и есть смысл вынесения политик в данные.

6. [1.3] Что произойдёт через месяц, если модель уберут из каталога или поменяют цены? Как ваш код это переживёт?

Каталог — данные, а не код: правится конфиг, selectModel автоматически построит новую цепочку. Если выбранная модель отключена провайдером, сработает fallback (и это видно в fallbackFrom). Важно хранить дату проверки цен.

7. [1.4] Почему время и имя пользователя находятся в конце, а не в system? Что случится с кэшем, если перенести их в начало?

Кэш работает по совпадающему префиксу. Если в начале лежит то, что меняется на каждом запросе, префикс «ломается» сразу и кэшировать нечего — платим полную цену за статику (инструкции, документ) каждый раз.

8. [1.4] Назовите два случая, когда отбор по общим словам не найдёт ответ, хотя он есть в регламенте. Что предложите?

Синонимы/перефразирование («отпуск» и «ежегодные выходные»), опечатки, другой язык вопроса. Решение — векторный поиск (эмбеддинги) или гибрид с ключевым поиском (модуль 5) и контрольный набор вопросов для измерения полноты.

9. [1.5 × 1.3] Почему fallback срабатывает на 503, но не на 401? Чем опасен переход на другую модель при 400?

503 — проблема провайдера, другая модель может ответить. 401 — неверный ключ, 400 — неверный запрос: другая модель получит тот же ошибочный запрос, мы потратим время и скроем баг, который нужно чинить.

10. [1.5 × 1.2] Как добавить стриминг в ask() и что изменится в учёте стоимости и обработке ошибок?

Использовать client.stream: пользователь видит текст сразу. Стоимость считается по usage из финального события (нужен include_usage); ошибка может случиться посреди ответа, поэтому нужна политика «показать частичный ответ или отменить»; повторять запрос после первых токенов нельзя.
