Module 3

AI-assisted SDLC with coding agents

The goal is to learn to work with a coding agent as a managed process: rules → specification → implementation with tests → review → PR. The result is a way of working, not code, so what gets checked are artefacts: rule files, the specification, commit history, the docs/notes.md log, the PR and the decisions note.

How to work through the module. Do the theory courses first, then tasks 3.1–3.5 in order, then the final task. If you already know a task's topic well, you can skip the details, but the files from the task must still exist: the final task builds on CLAUDE.md from 3.1, Spec Kit from 3.3, the hooks, the /new-endpoint command and the GitHub repository from 3.5. The module is complete when the final task meets all criteria.
How it is checked. You check every task yourself, the final one included. Order: do the task → go through the criteria → only then open the sample solution and compare. Each criterion is checked with a command, with git, or with an entry in docs/notes.md. If a criterion is not met, go back to the task, not to the solution. Commit the docs/notes.md entries together with the task's work.
Tool and stack: the main tool is Claude Code, and everything mandatory is done in it. Copilot and Cursor appear only in optional steps for those who use them, and in an optional comparison. The practice project uses TypeScript, Node.js 20+, Express, Vitest and ESLint.
Commands can be copied. Code blocks have a "Copy" button, and dotted commands inside text, such as npm run check, are copied on click or from the keyboard (Tab, then Enter).

Terms

Term Meaning
Deterministic check A check that always gives the same result on the same code: types (tsc), the linter, tests. Unlike an agent's answer.
Ping-pong First the agent writes tests for a rule and they fail (ping), then it changes the code until they pass (pong). Each step is a separate commit.
Navigator and driver Roles from pair programming. The navigator (you) sets the direction, checks, stops and rolls back. The driver (the agent) writes the code.
Constitution A Spec Kit file with rules that apply to every feature in the project, such as "tests first" or "no new dependencies".
NEEDS CLARIFICATION A marker Spec Kit puts in the specification where requirements are missing. It is a question for you.
Hook Your script, which Claude Code runs by itself before a tool call (PreToolUse) or after it (PostToolUse). It can block the call. Unlike a rule in CLAUDE.md, it cannot be "forgotten".
MCP Model Context Protocol — a standard way to connect an external service (issue tracker, database, browser) to the agent as a set of tools.
$ARGUMENTS The place in a custom command where everything you type after its name is inserted: /new-endpoint GET /books/:id.
/compact and /clear /compact condenses the session history into a summary, and the agent continues with what it learned. /clear erases the history completely.
AI Champion A person on the team who collects shared agent settings (rules, commands, hooks) in the repository and makes sure everyone uses them.
Cycle time, baseline Cycle time is the time from starting a task to closing it. The baseline is the metric's value before AI was introduced, which the later value is compared with.

  id: number;
  title: string;
  author: string;
  read: boolean;
}

export class BookNotFoundError extends Error {}

let nextId = 1;
export const books = new Map<number, Book>();

export function addBook(title: string, author: string): Book {
  const book: Book = { id: nextId++, title, author, read: false };
  books.set(book.id, book);
  console.log("book added", book.id);
  return book;
}

export function listBooks(): Book[] {
  return [...books.values()];
}

export function getBook(id: number): Book {
  const book = books.get(id);
  if (!book) {
    throw new BookNotFoundError(String(id));
  }
  return book;
}

export function recent(n = 3): Pick<Book, "id" | "title">[] {
  const all = listBooks();
  return Array.from({ length: n }, (_, i) => {
    const book = all[all.length - i];
    return { id: book.id, title: book.title };
  });
}

export function paginate<T>(items: T[], page: number, perPage: number): T[] {
  // pages are numbered from 1
  const start = page * perPage;
  return items.slice(start, start + perPage);
}

export function markRead(id: number): Book {
  const book = getBook(id);
  book.read = true;
  return book;
}

Task 3.1

Agent rules: project and personal

Courses: Claude Code in Action; GitHub Copilot Capabilities; Cursor Basics 101; AI-Native SDLC Time: ~50 min Branch: main, no separate branch

What we do

Set up permanent rules for the agent at three levels: project rules for the team, a personal rule for this project, and a personal rule for all your projects.

Why

Without rules the agent writes "generic" code every time. Project rules live in the repository and the whole team sees them. Personal rules never reach the repository. The agent knows Express and TypeScript from open-source code, but your own conventions, such as the src/log.ts logger, must be described.

Steps

  1. Before the rules. Open Claude Code in the shelf folder and ask: "add logging to the POST /books/:id/read handler". Note what the agent actually logs with, and record the real result, not the expected one. Either outcome is fine: the agent may use console.log, as src/server.ts and src/storage.ts do, or it may pick up getLogger() from src/log.ts by itself, because the neighbouring code in src/app.ts is built that way. The second case is already correct behaviour without any rules. Then undo the change: git restore ., and delete new files by hand. git status must show "nothing to commit".
  2. CLAUDE.md — team rules. Create CLAUDE.md in the root of shelf/, next to package.json. It has four sections: Stack, Commands, Conventions, Prohibitions. It must say: log only through getLogger() from src/log.ts; API errors are { detail } with a status code; tests go in tests/. Prohibitions: do not change files outside the task, do not add dependencies without being asked, do not push or merge. Commit: git add CLAUDE.md && git commit -m "chore: add CLAUDE.md".
  3. CLAUDE.local.md — personal, for this project. Create the file in the same folder, for example with your command for running tests. It must not reach git: check git status.
  4. ~/.claude/CLAUDE.md — personal, for all projects. Append to the end of the file (create it if it doesn't exist): "Reply briefly. Write in British English (colour, behaviour). End each reply with the line — ok". This rule is visible straight away and easy to check.
  5. docs/notes.md. In section 3.1, write 3–4 lines on what rules live where and why. Separately, explain why the Express and TypeScript stack was chosen: what the agent knows about it from open-source code.
  6. After the rules. Repeat step 1 in a new session. Record in docs/notes.md what the agent logs with now. Then undo the change: git restore src/. You will do the full logging change in 3.4 (B-6).
  7. Optional, if you use Copilot or Cursor: put the same project rules in .github/copilot-instructions.md or .cursor/rules, as each tool requires.

Task 3.2

Debugging, tests and decomposition

Courses: AI-Assisted Engineering; Cursor Basics 101 Time: ~60 min Branch: main, no separate branch

What we do

Write prompts for tests, for fixing a bug, for analysing a compiler error, and for splitting a task into parts.

Why

If you give the agent only the code, it writes tests that confirm the bug. If you only say "fix it", the fix is a guess. If the agent invents a function that doesn't exist in the library, a check must catch it, not a hunch.

Steps

  1. B-1: tests from the code only. Open Claude Code and ask: "Write tests for percent() in src/stats.ts, don't change the code". Run npm test. There are two outcomes; record yours:
    • Green. The agent derived the expectations from the formula itself and locked the bug in as the norm: 5 of 10 gives 0.5, not 50. The tests compare the code with itself.
    • The agent found the bug itself. Modern models often notice a mismatch between code and purpose — here the function name, the word "percentage" in the comment and the multiplication instead of division are enough. It then proposes tests based on meaning that fail, and that is correct behaviour, not a flaw in the task.
    Delete the tests and record your case in docs/notes.md: why green tests prove nothing — or what made the agent suspect a bug. The conclusion is the same: tests derived from code only check that "the code works the way it is written". The source of truth is the expected behaviour, and you must supply it: a function more complex than percent() will give no hints in the code.
  2. B-1: tests based on meaning. Repeat the request, adding the function's purpose and examples: "percent(read, total) is the share of read books as a percentage. Examples: 5 of 10 — 50; 1 of 3 — 33.3; 0 books — 0; 10 of 10 — 100. The tests check this behaviour, not the current code". File: tests/stats.test.ts. Run the tests: they must fail.
  3. B-1: the fix. Ask the agent to fix percent() so the tests pass, without changing the tests. Commit the tests and the fix as two commits.
  4. B-2: three-part prompt. Reproduce the error. In the first terminal: npm run dev. In the second: curl -X POST localhost:3000/books -H "Content-Type: application/json" -d '{"title":"Dune","author":"Herbert"}', then curl localhost:3000/books/recent. A TypeError and stack trace appear in the first terminal. The prompt must have three parts: the exact error message, the recent() function from src/storage.ts, and the expected behaviour: return up to three latest books, newest first; for an empty list — an empty array. Ask for a fix and for tests with 0, 1 and 5 books. Record the prompt in docs/notes.md.

Task 3.4

Agent mode, "tests first" and verification

Courses: Structured Vibe Coding; EngX.AI Bootcamp; GitHub Copilot Capabilities Time: ~60 min Branch: task-3.4 from a fresh main; merge at the end of the task

What we do

Work with the agent in a "tests → code → check" loop, then change logging across several files in agent mode.

Why

The agent's output is non-deterministic, so it is combined with checks: types, the linter and tests. Regressions from earlier changes are caught by re-running old tests.
