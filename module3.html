Модуль 3

AI-assisted SDLC с coding agents

Цель модуля — научиться работать с coding agent как с управляемым процессом: правила → спецификация → реализация с тестами → проверка → PR. Результат модуля — способ работы, а не код. Поэтому проверяются артефакты: файлы правил, спецификация, история коммитов, журнал docs/notes.md, PR и заметка о решениях.

Как проходить модуль. Сначала курсы теории, затем задания 3.1–3.5 по порядку, затем итоговое. Если тему задания вы уверенно знаете, можно не разбираться в ней подробно, но файлы из задания всё равно должны появиться: итоговое задание опирается на CLAUDE.md из 3.1, Spec Kit из 3.3, hooks, команду /new-endpoint и репозиторий на GitHub из 3.5. Модуль засчитан, когда итоговое задание выполнено по всем критериям.
Как проверяется. Все задания, включая итоговое, вы проверяете сами. Порядок: сделали задание → прошли по критериям готовности → только потом открыли пример решения и сравнили. Каждый критерий проверяется командой, через git или по записи в docs/notes.md. Если критерий не выполнен, вернитесь к заданию, а не к решению. Записи в docs/notes.md коммитьте вместе с работой задания.
Инструмент и стек: основной инструмент — Claude Code, всё обязательное делается в нём. Copilot и Cursor — только в необязательных шагах для тех, кто ими пользуется, и в необязательном сравнении. Учебный проект: TypeScript, Node.js 20+, Express, Vitest, ESLint.
Команды копируются. У блоков кода есть кнопка «Копировать», а команды внутри текста — пунктирные, вроде npm run check — копируются по клику или с клавиатуры (Tab, затем Enter).

Термины модуля

Термин Что значит
Детерминированная проверка Проверка, которая на одном и том же коде всегда даёт один результат: типы (tsc), линтер, тесты. В отличие от ответа агента.
Ping-pong Сначала агент пишет тесты на правило и они падают (ping), потом меняет код, пока тесты не пройдут (pong). Каждый шаг — отдельный коммит.
Navigator и driver Роли из парного программирования. Navigator (вы) задаёт направление, проверяет, останавливает и откатывает. Driver (агент) пишет код.
Constitution Файл Spec Kit с правилами, которые действуют для каждой фичи проекта: например, «тесты сначала», «без новых зависимостей».
NEEDS CLARIFICATION Метка, которую Spec Kit ставит в спецификации там, где требований не хватает. Это вопрос к вам.
Hook Ваш скрипт, который Claude Code запускает сам до вызова инструмента (PreToolUse) или после него (PostToolUse). Может заблокировать вызов. В отличие от правила в CLAUDE.md, его нельзя «забыть».
MCP Model Context Protocol — стандартный способ подключить агенту внешний сервис (трекер задач, базу, браузер) как набор инструментов.
$ARGUMENTS Место в тексте своей команды, куда подставляется всё, что вы написали после её имени: /new-endpoint GET /books/:id.
/compact и /clear /compact сжимает историю сессии в краткое изложение, и агент продолжает с тем, что узнал. /clear стирает историю полностью.
AI Champion Человек в команде, который собирает общие настройки агента (правила, команды, hooks) в репозитории и следит, чтобы ими пользовались все.
Cycle time, базовая линия Cycle time — время от начала работы над задачей до её закрытия. Базовая линия — значение метрики до внедрения AI, с которым сравнивают значение после.

Репозиторий на GitHub

Сделайте это сразу: в 3.5 нужны Issues, а в итоговом задании — PR. На GitHub создайте репозиторий shelf без README и .gitignore — пустой, чтобы ваша история встала на него без конфликтов. Приватный или публичный — на ваш выбор: Issues, PR и GitHub MCP работают одинаково. Приватный просто аккуратнее (проект учебный, с намеренными багами и вашими заметками), но ничего в модуле от этого не зависит, а видимость потом меняется в Settings. Затем из папки shelf: 

git remote add origin https://github.com/<ваш-логин>/shelf.git
git push -u origin main

Проверка: на странице репозитория видна ветка main и ваш первый коммит. Если репозиторий уже создан и назван иначе — ничего не меняйте, дальше в модуле работайте с ним.

Как устроен git в модуле

Где Ветка Как попадает в main
3.1, 3.2 сразу main обычные коммиты, ветка не нужна
3.3 git switch -c 001-… по имени каталога фичи, который создал шаг specify коммиты в этой ветке, затем локально: git switch main && git merge <имя ветки>
3.4 git switch -c task-3.4 локально: git switch main && git merge task-3.4
3.5 git switch -c task-3.5 локально: git switch main && git merge task-3.5, затем git push origin main
Итоговое git switch -c 002-… по имени каталога фичи, который создал шаг specify через PR на GitHub, merge в интерфейсе GitHub, затем git switch main && git pull

Где в таблице написано <имя ветки> или 001-…, подставьте настоящее имя ветки из git branch.

Push и merge делаете вы, а не агент — это запрет из CLAUDE.md. Агент пишет код и коммитит, вы читаете diff, сливаете ветки и делаете push, а в итоговом задании открываете PR. Новую ветку всегда начинайте от свежего main: git switch main, затем git switch -c ….

Зачем

Без правил агент каждый раз пишет «типовой» код. Правила проекта лежат в репозитории и видны всей команде. Личные правила в репозиторий не попадают. Агент знает Express и TypeScript по открытому коду, а ваши конвенции, например логгер src/log.ts, нужно описать.

Условие

  1. До правил. Откройте Claude Code в папке shelf и попросите: «добавь логирование в обработчик POST /books/:id/read». Запомните, чем агент логирует на самом деле, и запишите фактический результат, а не ожидаемый. Вариантов два, и оба нормальны: агент может взять console.log — так логируют src/server.ts и src/storage.ts, — а может сам подхватить getLogger() из src/log.ts, потому что именно так устроен соседний код в src/app.ts. Второй случай — это уже корректное поведение без всяких правил. Затем откатите правку: git restore ., новые файлы удалите вручную. git status должен показать «nothing to commit».
  2. CLAUDE.md — правила команды. Создайте CLAUDE.md в корне shelf/, рядом с package.json. В нём четыре раздела: Стек, Команды, Конвенции, Запреты. Обязательно запишите: логирование только через getLogger() из src/log.ts; ошибки API — в виде { detail } с кодом статуса; тесты в tests/. В запретах: не менять файлы вне задачи, не добавлять зависимости без запроса, не делать push и merge. Закоммитьте: git add CLAUDE.md && git commit -m "chore: add CLAUDE.md".
  3. CLAUDE.local.md — личное для этого проекта. Создайте файл в той же папке, например с вашей командой запуска тестов. Он не должен попасть в git: проверьте git status.
  4. ~/.claude/CLAUDE.md — личное для всех проектов. Допишите в конец файла (если его нет, создайте): «Отвечай кратко. Пиши по-британски (colour, behaviour). Заканчивай ответ строкой — ok». Это правило видно сразу, его легко проверить.
  5. docs/notes.md. В раздел 3.1 в 3–4 строках напишите: что из правил где лежит и почему. Отдельно напишите, почему выбран стек Express и TypeScript: что агент знает о нём из открытого кода.
  6. После правил. Повторите шаг 1 в новой сессии. Запишите в docs/notes.md, чем агент логирует теперь. Затем откатите правку: git restore src/. Логирование целиком сделаете в 3.4 (B-6).
  7. Необязательно, если используете Copilot или Cursor: те же правила проекта положите в .github/copilot-instructions.md или .cursor/rules, как требует каждый инструмент.
В Copilot и Cursor (необязательно)

Для тех, кто работает в Copilot или Cursor. Остальные могут пропустить этот блок.

Правила проекта.
  • Аналог: в Copilot — .github/copilot-instructions.md, в Cursor — .cursor/rules/*.mdc. Оба читают и AGENTS.md. Файл попадает в контекст каждого запроса сам.

Личные правила для всех проектов.
  • Аналог: в Cursor — User Rules (Cursor Settings → Rules), действуют в каждом проекте. В Copilot — пользовательские instructions в настройках VS Code.
  • С чем путают: .cursor/rules/*.mdc лежит в репозитории и действует только на этот проект для всей команды.

Критерии готовности

  • CLAUDE.md короче 60 строк и содержит четыре раздела: стек, команды, конвенции, запреты. В конвенциях есть getLogger() и { detail }.
  • git ls-files CLAUDE.local.md ничего не выводит, а git status не показывает этот файл.
  • Личное правило работает в другой папке: cd /tmp && claude, любой вопрос — короткий ответ с британским написанием и строкой — ok в конце.
  • В новой сессии агент использует getLogger, а не console.log. В docs/notes.md записано, что было до и после CLAUDE.md — в том числе если «до» агент уже сам выбрал getLogger и правило лишь закрепило конвенцию.
  • В docs/notes.md раздел 3.1 заполнен: что где лежит, почему, и обоснован выбор стека.
  • К итогу модуля git log --oneline -- CLAUDE.md показывает не меньше трёх коммитов: создание и две правки.
Подсказки
  • /init создаёт черновик CLAUDE.md. Сократите его: агент читает файл в каждой сессии.
  • Три уровня: CLAUDE.md — команда и проект, CLAUDE.local.md — вы и проект, ~/.claude/CLAUDE.md — вы и все проекты.
  • Личное правило проверяйте на вопросе, где ответ заметно меняется: строка в конце, британское написание, короткий ответ.

Задание 3.2

Отладка, тесты и декомпозиция

Курсы: AI-Assisted Engineering; Cursor Basics 101 Время: ~60 мин Ветка: main, отдельная не нужна

Что делаем

Пишем промпты для тестов, для исправления ошибки, для разбора ошибки компилятора и для разбиения задачи на части.

Зачем

Если дать агенту только код, он напишет тесты, которые подтверждают баг. Если сказать только «почини», исправление будет наугад. Если агент придумал функцию, которой нет в библиотеке, поймать это должна проверка, а не догадка.

Условие

  1. B-1: тесты только по коду. Откройте Claude Code и попросите: «Напиши тесты для percent() в src/stats.ts, код не меняй». Запустите npm test. Исходов два, записывайте свой:
    • Зелёные. Агент вывел ожидания из самой формулы и зафиксировал баг как норму: 5 из 10 даёт 0.5, а не 50. Тесты сравнивают код с самим собой.
    • Агент сам нашёл баг. Современные модели часто видят расхождение кода и назначения — здесь хватает имени функции, слова «проценты» в комментарии и умножения вместо деления. Тогда он предложит тесты по смыслу, которые падают, и это правильное поведение, а не ошибка задания.
    Удалите тесты и запишите в docs/notes.md свой случай: почему зелёные тесты ничего не доказывают — или по каким признакам агент заподозрил баг. Вывод один: тесты из кода проверяют лишь «код работает так, как написан». Источник истины — ожидаемое поведение, и задать его должны вы: на функции сложнее percent() подсказок в коде не будет.
  2. B-1: тесты по смыслу. Повторите просьбу, добавив назначение функции и примеры: «percent(read, total) — доля прочитанных книг в процентах. Примеры: 5 из 10 — 50; 1 из 3 — 33.3; 0 книг — 0; 10 из 10 — 100. Тесты проверяют это поведение, а не текущий код». Файл: tests/stats.test.ts. Запустите тесты: они должны упасть.
  3. B-1: исправление. Попросите исправить percent() так, чтобы тесты прошли, тесты при этом не менять. Закоммитьте тесты и исправление двумя коммитами.
  4. B-2: промпт из трёх частей. Воспроизведите ошибку. В первом терминале: npm run dev. Во втором: curl -X POST localhost:3000/books -H "Content-Type: application/json" -d '{"title":"Дюна","author":"Герберт"}', затем curl localhost:3000/books/recent. В первом терминале появится TypeError и стек.   • Тесты B-1 падают на исходном коде и проходят после исправления. Тесты между этими состояниями не менялись.
  • Промпт для B-2 из трёх частей записан в docs/notes.md.
  • В docs/notes.md: ошибка tsc из шага «Галлюцинация», ссылка на документацию и ваш промпт с обратной связью.
  • В docs/B-4.md 4–6 подзадач, и про каждую вы можете сказать, что она даёт сама по себе. Есть хотя бы один вложенный пункт, хотя бы одна приписка «зависит от» и один открытый вопрос к владельцу продукта.
Подсказки
  • Сначала добейтесь, чтобы тест упал, и только потом исправляйте код. Тест, который не падал ни разу, ничего не доказывает.
  • Почему tsc не заметил ошибку в recent()? Посмотрите опцию noUncheckedIndexedAccess в tsconfig.json: это ещё одна детерминированная проверка.
  • Стек берите из вывода npm run dev, а не из тестов: в тестах Express стек не печатает.
  • Обратная связь агенту — это факт: точное сообщение компилятора и то, что вы нашли в документации, а не «попробуй ещё».

Задание 3.3

Spec Kit: от задачи к спецификации и плану

Курсы: Spec-Driven Development with GitHub Spec Kit; EngX.AI Bootcamp Время: ~60 мин, в первый раз — до 1,5 ч Ветка: 001-… по имени фичи, создаёте сами после /speckit-specify; в конце сливаете в main

Что делаем

Доводим B-4 (экспорт библиотеки) через Spec Kit до спецификации, плана и списка задач. Код не пишем.

Зачем

Неточное требование — главная причина того, что агент делает «не то». Спецификация задаёт цель и критерии приёмки. Правила, которые действуют во всех шагах, живут отдельно — в constitution.

Условие

  1. Установка. В папке shelf выполните: uvx --from git+https://github.com/github/spec-kit.git specify init --here --integration claude. На вопрос про непустую папку ответьте «да» (или добавьте --force, чтобы не спрашивал). Если Spec Kit предложит добавить .claude/ в .gitignore, откажитесь: эти файлы нужны в репозитории в 3.5. Перезапустите Claude Code и закоммитьте: git add -A && git commit -m "chore: add Spec Kit".
  2. Constitution. Команды Spec Kit — это скиллы из .claude/skills/, а их список Claude Code читает при старте. Поэтому в сессии, которая была открыта до установки, команды не появятся: выйдите (/exit или Ctrl+D) и запустите claude заново — обязательно из папки shelf, иначе скиллы не найдутся. Проверка: наберите /speckit — в списке должны всплыть девять команд. Правила можно передать сразу аргументом, одной строкой: 
    /speckit-constitution только localhost (никаких внешних сервисов и сетевых вызовов);
тесты сначала (сначала падающий тест, потом код); без новых зависимостей
без обоснования
    Либо вызвать /speckit-constitution без аргументов и отвечать на вопросы — тогда формулировки придётся диктовать по ходу. Каждое правило должно проверяться ответом «да» или «нет»; расплывчатое «писать качественный код» не годится. Агент предложит черновик — прочитайте его и поправьте формулировки, прежде чем соглашаться. Результат — файл .specify/memory/constitution.md; других файлов этот шаг менять не должен.

  5. Clarify. Запустите /speckit-clarify и отвечайте на вопросы сами, как владелец продукта. Агент не должен решать за вас. Проверка: grep -rn "NEEDS CLARIFICATION" specs/ ничего не выводит.

  7. Tasks. Запустите /speckit-tasks, появится tasks.md. Закоммитьте всё: git add -A && git commit -m "docs: spec for export (B-4)".
  8. docs/notes.md. Запишите порядок команд, которые вы выполнили, и какой файл создал каждый шаг. Реализацию делать не нужно.
